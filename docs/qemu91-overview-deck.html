QEMU i.MX 91 — boot the real software stack,
no silicon required.

A complete functional model of the i.MX 91 SoC in QEMU. It boots U-Boot and a stock NXP BSP Linux on a virtual i.MX 91 — exactly as the silicon would. The i.MX 91 is the entry part of the i.MX 9 family: a single Cortex-A55, and no System Manager, so Linux programs the clock and power blocks directly.

Honest limits

What doesn't work — and why

Every gap has one of two causes: a per-die secret that can't be faked, or a block the i.MX 91 silicon simply does not have. Nothing is hand-waved — and the list is short by design.

No GPU · no VPU · no NPU · no 2D engine
Not a gap — the SoC has none of these. The i.MX 91 is the cost-optimized entry part: no Mali, no Wave codec, no Ethos NPU, no PXP. There is nothing to model and nothing missing.
Secure boot · EdgeLock crypto services
Depend on per-die secrets (HUK, fused keys) that physically can't be modeled. Fuse reads work (plain data); the crypto engine is out of scope by design — and unused in emulation.
Partial-coverage blocks: pin-mux / syscfg · FlexIO non-I²C modes
Modeled to the level the BSP exercises. IOMUXC / SRC / blk-ctrl are logging stubs — pad muxing and reset routing have no meaning in emulation (QEMU doesn't wire physical pins). FlexIO is modeled as an I²C master; its SPI/UART/PWM shifter modes have no BSP user. Boot and every datapath work regardless.
ELE GET_INFO soc-id (shared model)
The EdgeLock model returns the i.MX 93's id, so the SE driver logs a benign index miss. SoC identity is still correct — the SiP SoC-info SMC reports i.MX 91, verified — so it's a documented cosmetic quirk, not a functional gap.
The pattern:  if it's closed firmware or silicon secrets, we model the interface and stop at the engine. If it's a QEMU limitation, we work around it transparently and write down why. On the i.MX 91 there's little to leave out — the simplest i.MX 9 is also the most completely modeled.
